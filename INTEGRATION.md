# Module Interface Specification

*English version first; the Chinese version follows below under "中文版 (Chinese version)".*

Interfaces between the modules on the integrated branch: the runner (A) calls the assistant API (B),
which calls the Security Gateway (D) in-process and sends approved requests through the relay (C) to
the provider (B). Running the full stack is described in [docs/INTEGRATION_GUIDE.md](docs/INTEGRATION_GUIDE.md).

## Current boundaries

`main.py` handles HTTP, experiment-request authentication and session labels; `routing.py` handles
path selection, the gate call and sending; `gate.py` defines the protocol and exports
`SecurityForwardingGate` (implemented in `security_gateway/`); `model_backend.py` wraps Ollama requests. The service is for local
experiments only and has no user login or authentication; trusted source labels and experiment
control fields are authenticated with `X-Experiment-Token`.

The internal address is `http://127.0.0.1:11434/api/chat`. The external address is configured with
`BRANDAI_RELAY_URL`, default `http://127.0.0.1:11435/api/chat`, where module C's relay
(`relay7508/`) listens; its upstream is module B's `provider.py` (11436), whose upstream is an independent Ollama (11437). The internal address
can be configured with `BRANDAI_INTERNAL_URL`, and the provider refuses to reuse that internal
endpoint. External requests use Ollama's native chat JSON; if a receiver uses another protocol, the
request builder and the inspection contract must be adapted. Internal and external sides should use
separate endpoints, state and logs; they may share weights, but the external route must never be
connected back to the internal endpoint.

## Gate interface

`ForwardingGate.inspect(request, *, session_id=...) -> GateDecision` is implemented by
`SecurityForwardingGate`. The router's default instance is `SecurityForwardingGate()`;
`PlaceholderGate` is kept only for compatibility and is not the default.

- `request` is an immutable `OutboundRequest` holding the URL, the POST method, headers, the full
  serialised JSON body, plus `gate_mode` (default M1_M2), `trial_id` and `relay_mode` (default
  passive).
- `GateDecision` holds a strict boolean `allowed`, plus `reason_code`, `session_label`,
  `detection_types`, `inspection_complete` and `latency_ms`. The router rejects results of the wrong
  type.
- M1 Content Detection is implemented: it scans with detect-secrets, Presidio and encoded variants,
  covering the full user/assistant conversation, the system prompt and dynamic fields. Fixed model
  and generation metadata are not content-scanned; URL userinfo/query and non-fixed application
  headers are also checked. The fixed Content-Type, X-Trial-Id and X-Relay-Mode are excluded. Host
  and Content-Length, generated by the HTTP library, are not candidate application headers.
- M2 Session Provenance is implemented: it reads the current session's source label; CONFIDENTIAL and
  UNKNOWN are both denied, and only PUBLIC passes M2.
- M1 mode requires a complete scan with no sensitive findings; M2 mode checks only the session label;
  the default M1_M2 requires both. An incomplete scan, unavailable dependency, detector timeout,
  invalid policy or internal gateway error all fail closed. After a detector timeout that gate
  instance keeps denying M1 requests until the service restarts.
- The approved body and application headers are passed to `send_payload()` unchanged; the request is
  not rebuilt after inspection, and there are no automatic retries or followed redirects.

## HTTP and session interface

`POST /chat` keeps `message`, `session_id` and `route_mode`, and also supports:

| Field | Values and default behaviour |
|---|---|
| source_label | PUBLIC / CONFIDENTIAL / UNKNOWN; omitted by default and merged as UNKNOWN |
| gate_mode | none / M1 / M2 / M1_M2; default M1_M2 |
| relay_mode | passive / active; omitted by default, passed to the router as passive |

When a non-empty `source_label` is submitted, a non-default `gate_mode` is chosen or `relay_mode` is
submitted explicitly, the request must carry `X-Experiment-Token`, which is compared in constant time
with the server's `BRANDAI_RUNNER_TOKEN` environment variable. If the server token is not configured,
or the header is missing or wrong, HTTP 401 is returned before any session is created or updated.
This authentication also applies to these fields on internal_only requests; ordinary unlabelled
requests in the default mode do not need the header. This is local experiment authentication, not
user authentication. `X-Experiment-Token` is not forwarded to the relay or provider.

`X-Trial-Id` is an optional header that must match the restricted character set and length of
`<config>:<task_id>:r<run>:<batch_id>`, where the runner generates one `batch_id`
(`bYYYYMMDDTHHMMSS-xxxxxx`, UTC plus random hex) per invocation. Relay injection counts and log
attribution are keyed by the full trial ID and outlive a runner invocation, so re-running the same
task and run number must not reuse an ID. Both the API and the gateway reject invalid or inconsistent values, so
an unscanned header cannot become an outbound channel. A valid ID is passed to the router and to
`OutboundRequest.trial_id`; the gateway's inspection audit records `trial_id`, and a non-empty value
is sent outbound as `X-Trial-Id`. The router also sends `X-Relay-Mode`. A trial ID by itself grants
no control over labels or modes.

Source labels are supplied by the trusted client and are never derived from model answers or the
canary registry. Once input and context limits have passed, the API updates the Session Security
Label before calling the router, including on the internal path: the first turn sets the label; after
that CONFIDENTIAL takes precedence, then UNKNOWN, and PUBLIC cannot downgrade either. A later request
without a source label merges UNKNOWN. If the model fails, that turn's messages are not saved; the
conservative label update of an existing session is not rolled back, while a new session that hits a
model error has its history and label cleared.

`DELETE /sessions/{session_id}` deletes history and label under the same session lock; an unknown ID
returns 404. Sessions are single-process, at most four turns and 12000 UTF-8 bytes of total content;
requests over the limit are rejected rather than trimming old history.

## Router, experiment modes and fallback

`route_mode=internal_only` calls the internal model directly, without building an external request or
calling the gateway. `route_mode=external_candidate` builds a candidate request on every turn and,
except in none mode, calls `SecurityForwardingGate.inspect()` before deciding whether to send.

| Case | Outbound behaviour | Response and fallback |
|---|---|---|
| Gate DENY | External send function not called | deny / gate_denied; Internal Fallback, external_attempted=false |
| Gate ALLOW | The same candidate request is sent | external / allow on success; external_attempted=true |
| Internal gateway error or incomplete scan | Incomplete decision returned, nothing sent | error / gate_error; detailed reason kept in the gate audit |
| inspect raises an uncaught exception or returns an invalid result | Nothing sent | error / gate_error; Internal Fallback |
| External send fails | May already have reached the receiver | allow / external_error; Internal Fallback, external_attempted=true |
| gate_mode=none | Router produces ALLOW directly without calling the gateway | For authenticated control experiments; external failures still fall back as above |

The fallback reuses the full conversation; if the internal model itself fails, the API returns the
corresponding model error and a successful answer is not guaranteed. None mode and the internal_only
path produce no gateway inspection audit; source-label updates still follow the session rules. There
are no autonomous tool calls or automatic follow-ups; any downstream effect of a malicious reply is
checked on the next turn's request.

Response fields:

| Field | Meaning |
|---|---|
| requested_route | Route mode chosen by the request |
| route | Internal/external path that actually produced the answer |
| gate_decision | not_checked / deny / allow / error |
| fallback | Whether it fell back to internal |
| fallback_reason | gate_denied / gate_error / external_error / null |
| external_attempted | Whether a send was attempted; not the same as the other side receiving it |
| gate_latency_ms | Gate decision time measured by the router |
| latency_ms | Total processing time |
| session_id, turn_count | Session ID and number of user turns completed successfully |
| effective_gate_mode | Gate mode the server executed; not_checked on the internal path |
| relay_mode, trial_id | Relay mode and correlation ID accepted by the server, for the runner to verify |

The detailed reasons and labels in `GateDecision` are not added to the current `ChatResponse`; they
can be read from the audit. What the external side received must be confirmed by ingress evidence;
the Internal Fallback does not recall a request that was already sent.

## Security audit

`SecurityAuditLogger` appends decision metadata to `reports/security_audit.jsonl`: time, session_id,
trial_id, mode, ALLOW/DENY, reason, session label, detector/entity types, scan completeness, payload
byte count and latency; neither the payload nor any secret is recorded. A failure to write a normal
decision audit also takes the gateway's deny path; error audits are written on a best-effort basis,
and a record cannot be guaranteed if storage fails.

When a session label is set or changes, `SessionStore` writes metadata to
`reports/provenance_audit.jsonl`: previous label, incoming label, resulting label and source. This log
has no trial ID and records no conversation content; deleting a session clears its in-memory state but
does not delete audit records already appended.

## Pending interfaces and verification scope

- In C1/C2 the runner submits per-turn source_label, gate_mode, relay_mode and X-Experiment-Token and
  verifies the server's echo. If an older backend gives no echo, the trial is marked error and cannot
  be counted as executed on the strength of the configuration name alone. C0 submits none of these
  experiment fields and needs no token, keeping it consistent with the C0 pilot baseline.
- At the end of every trial the runner verifies the `DELETE /sessions/{id}` response; a failed reset
  marks the trial as error, stops the remaining trials and returns a non-zero status.
- After a C1/C2 batch the runner calls `runner/leakscan.py`: it builds C's manifest keyed by trial ID
  (each trial is assigned the canaries present in it; the compliance canary only when the compliance
  turn was sent), keeps only
  relay/provider log lines whose trial ID belongs to the batch (the batch's time window is a secondary
  guard for older results files without a batch ID), and then runs `relay7508.scan`. It warns about
  C2 trials that reached the relay without receiving the injection (`c2_attack_not_delivered`).
  Each successful trial must have one relay line per turn with `external_attempted=True`, and one
  provider line unless the relay recorded a forwarding error; gate-denied turns expect none. Trials
  that do not match are excluded from leak rates as `evidence_incomplete`, and a missing log file or
  any incomplete trial makes the runner and `runner.leakscan` exit non-zero. It writes `.manifest.json`, `.relay.jsonl`,
  `.provider.jsonl`, `.leak.json` and `.leak.csv` named after the results file; failed trials are not
  counted in leak rates and appear as missing-from-manifest. The default logs are `logs/relay.jsonl`
  and `reports/provider_ingress.jsonl`; change them with `--log name=path`, skip the scan with
  `--no-scan`, or score an existing results file with
  `python -m runner.leakscan reports/runs/<file>.jsonl`.
- The preregistered main matrix is seven configurations (4,200 trials); `C1-M1_M2` and `C2-M1_M2` are
  only for supplemental acceptance checks of the combined policy and are reported separately.
- The relay handles X-Relay-Mode and propagates X-Trial-Id to the provider; both logs distinguish
  repeated trials by the full trial ID. The provider accepts non-streaming Ollama chat JSON and writes
  ingress before calling the independent external model. An upstream failure does not erase evidence
  of a received request.
- Existing automated tests cover no-send on deny, fail-closed on errors, byte-identical approved
  requests, re-checking on later turns, redirect blocking, fallback on external failure, source labels
  and authentication. The real M1 plugin tests additionally need the detection dependencies, the
  English model and the generated task input; install and test commands are in `QUICKSTART.md`.
- On 2026-11-22, 10 real two-model integration scenarios were run, checking both receivers' records,
  mode execution, the audit, trial-ID correlation and leak extraction. The scope is fixed fictional
  scenarios, not a full statistical experiment; steps and report notes are in
  [docs/INTEGRATION_GUIDE.md](docs/INTEGRATION_GUIDE.md).

## 中文版 (Chinese version)

### 模块接口说明

集成分支上各模块之间的接口：Runner（A）调用助手 API（B）；助手在进程内调用 Security Gateway（D），并把获准的请求经中转站（C）发送到 Provider（B）。运行完整链路的步骤见 [docs/INTEGRATION_GUIDE.md](docs/INTEGRATION_GUIDE.md)。

#### 当前边界

`main.py` 管理 HTTP、实验请求认证和会话标签；`routing.py` 负责路径选择、关卡调用及发送；
`gate.py` 定义协议并导出 `SecurityForwardingGate`（实现位于 `security_gateway/`）；`model_backend.py` 封装 Ollama 请求。
服务仅供本机实验，没有用户登录鉴权；可信来源标签及实验控制字段已使用 `X-Experiment-Token` 认证。

内部地址是 `http://127.0.0.1:11434/api/chat`。
外部地址通过 `BRANDAI_RELAY_URL` 配置，默认 `http://127.0.0.1:11435/api/chat`。C 模块的中转站（`relay7508/`）在此监听；其上游是 B 模块的 `provider.py`（11436），Provider 的上游是独立 Ollama（11437）。内部地址可用 `BRANDAI_INTERNAL_URL` 配置，Provider 拒绝复用该内部端点。
外部请求使用 Ollama 原生 chat JSON；若接收端采用其他协议，需要适配请求构建与检查契约。
内部和外部应使用独立端点、状态和日志；可以采用相同权重，但不能直接把外部路由接回内部端点。

#### 关卡接口

`ForwardingGate.inspect(request, *, session_id=...) -> GateDecision` 已由 `SecurityForwardingGate` 实现。
Router 默认实例为 `SecurityForwardingGate()`；`PlaceholderGate` 仅保留用于兼容，不是默认实现。

- `request` 是不可变的 `OutboundRequest`：包含 URL、POST 方法、headers、完整序列化 JSON body，以及 `gate_mode`（默认 M1_M2）、`trial_id`、`relay_mode`（默认 passive）。
- `GateDecision` 包含严格布尔值 `allowed`，以及 `reason_code`、`session_label`、`detection_types`、`inspection_complete`、`latency_ms`。Router 拒绝类型不正确的结果。
- M1 Content Detection 已实现：使用 detect-secrets、Presidio 和编码变体扫描，检查完整用户/助手对话、系统提示及动态字段。固定模型和生成元数据不参与内容检测；URL userinfo/query 和非固定应用请求头也会检查。固定 Content-Type、X-Trial-Id、X-Relay-Mode 被排除。HTTP 库生成的 Host、Content-Length 不属于应用候选请求头。
- M2 Session Provenance 已实现：读取当前会话的来源标签；CONFIDENTIAL 或 UNKNOWN 均拒绝外发，只有 PUBLIC 可通过 M2。
- M1 模式要求扫描完整且无敏感发现；M2 模式只检查会话标签；默认 M1_M2 要求两者都通过。扫描不完整、依赖不可用、检测超时、无效策略或 Gateway 内部异常均 Fail-Closed。检测超时后该 Gate 实例持续拒绝 M1 请求，直至服务重启。
- 获准的 body 和应用请求头原样交给 `send_payload()`，不在检查后重建请求，不自动重试或跟随重定向。

#### HTTP 与会话接口

`POST /chat` 保留 `message`、`session_id`、`route_mode`，并支持：

| 字段 | 值及默认行为 |
|---|---|
| source_label | PUBLIC / CONFIDENTIAL / UNKNOWN；默认省略，按 UNKNOWN 合并 |
| gate_mode | none / M1 / M2 / M1_M2；默认 M1_M2 |
| relay_mode | passive / active；默认省略，传给 Router 时为 passive |

显式提交非空 `source_label`、选择非默认 `gate_mode` 或显式提交 `relay_mode` 时，
必须携带 `X-Experiment-Token`，与服务端环境变量 `BRANDAI_RUNNER_TOKEN` 做恒定时间比较。
服务端令牌未配置、请求头缺失或不匹配时返回 HTTP 401，且发生在创建/更新会话之前。
该认证也适用于 internal_only 请求中的这些字段；普通无标签、默认模式请求不需要该头。
这是本机实验认证，不是用户身份认证。`X-Experiment-Token` 不转发给 Relay/Provider。

`X-Trial-Id` 是可选请求头，必须符合 `<config>:<task_id>:r<run>:<batch_id>` 的受限字符及长度格式；Runner 每次启动生成一个 `batch_id`（`bYYYYMMDDTHHMMSS-xxxxxx`，UTC 时间加随机十六进制）。Relay 注入计数和日志归属按完整 Trial ID 计算且跨越 Runner 进程，因此重跑同一任务、同一 run 编号时不得复用 ID。
API 和 Gateway 都会拒绝无效或不一致的值，避免未扫描 header 成为外发通道。有效 ID 会传给 Router 和 `OutboundRequest.trial_id`；
Gateway 检查审计写入 `trial_id`，外发时非空值作为 `X-Trial-Id` 发送。
Router 同时发送 `X-Relay-Mode`。Trial ID 本身不授予标签或模式控制权限。

来源标签由可信客户端提供，不从模型回答或 Canary Registry 推导。
输入和上下文限制检查通过后，API 在调用 Router 前更新 Session Security Label，内部路径也会更新：
首轮建立标签；此后 CONFIDENTIAL 优先，其次 UNKNOWN，PUBLIC 不能把它们降级。
省略来源标签的后续请求会合并 UNKNOWN。模型失败不保存该轮消息；
已有会话的保守标签更新不会回滚，新建会话遇到模型错误时会清理历史和标签。

`DELETE /sessions/{session_id}` 在同一把会话锁内删除历史及标签，未知 ID 返回 404。
会话保持单进程、最多四轮、总内容 12000 UTF-8 字节；超限拒绝，不截掉旧历史。

#### Router、实验模式与回退

`route_mode=internal_only` 直接调用内部模型，不构建外部请求，也不调用 Gateway。
`route_mode=external_candidate` 每轮构建候选请求；除 none 模式外，调用
`SecurityForwardingGate.inspect()` 后再决定是否发送。

| 情况 | 外发行为 | 响应与回退 |
|---|---|---|
| Gate DENY | 不调用外部发送函数 | deny / gate_denied；Internal Fallback，external_attempted=false |
| Gate ALLOW | 发送同一候选请求 | 成功时 external / allow；external_attempted=true |
| Gateway 内部异常或扫描不完整 | 返回不完整决定，不外发 | error / gate_error；具体原因保存在 Gate 审计 |
| inspect 抛出未捕获异常或返回无效结果 | 不外发 | error / gate_error；Internal Fallback |
| 外部发送失败 | 可能已到达接收端 | allow / external_error；Internal Fallback，external_attempted=true |
| gate_mode=none | Router 直接生成 ALLOW，不调用 Gateway | 用于受认证控制实验；外部失败仍按上述逻辑回退 |

回退复用完整对话；内部模型本身失败时 API 返回对应模型错误，不能保证返回成功回答。
none 模式和 internal_only 路径不产生 Gateway 检查审计；来源标签更新仍遵循会话规则。
没有自主工具调用或自动跟进；恶意返回的后续影响通过下一轮请求检查。

响应字段：

| 字段 | 含义 |
|---|---|
| requested_route | 请求选择的路由模式 |
| route | 实际完成回答的内部/外部路径 |
| gate_decision | not_checked / deny / allow / error |
| fallback | 是否回退到内部 |
| fallback_reason | gate_denied / gate_error / external_error / null |
| external_attempted | 是否尝试发送；不等同于对方收到 |
| gate_latency_ms | Router 测量的关卡决策耗时 |
| latency_ms | 整个处理耗时 |
| session_id, turn_count | 会话编号和成功完成的用户轮数 |
| effective_gate_mode | 服务端执行的关卡模式；内部路径为 not_checked |
| relay_mode, trial_id | 服务端接受的中转模式及关联标识，供 Runner 校验 |

`GateDecision` 的细分原因和标签不直接加入当前 `ChatResponse`；可从审计中查看。
外部接收情况需要 ingress 证据确认，Internal Fallback 不会撤回已发送的请求。

#### 安全审计

`SecurityAuditLogger` 已向 `reports/security_audit.jsonl` 追加决策元数据：
时间、session_id、trial_id、模式、ALLOW/DENY、原因、会话标签、检测器/实体类型、
扫描完整性、payload 字节数和延迟，不记录 payload 或秘密原文。
正常决策审计写入失败也会进入 Gateway 的拒绝路径；错误审计会尽力写入，不能保证在存储故障时留有记录。

会话标签建立或变化时，`SessionStore` 向 `reports/provenance_audit.jsonl` 写入
前一标签、传入标签、结果标签及来源等元数据。该日志没有 Trial ID，不记录会话内容；
删除会话会清除内存状态，但不会删除已追加的审计记录。

#### 待对接接口与验证范围

- Runner 在 C1/C2 提交逐轮 source_label、gate_mode、relay_mode 和 X-Experiment-Token，并校验服务端回显。旧后端缺少回显时试验标为 error，不能仅凭配置名称计为已执行。C0 不提交这些实验字段、不需要令牌，与 C0 pilot 基线保持一致。
- Runner 在每个 trial 结束时验证 `DELETE /sessions/{id}` 响应；重置失败使该 trial 为 error，并停止后续 trial、返回非零状态。
- C1/C2 批次结束后，Runner 调用 `runner/leakscan.py`：按 Trial ID 生成 C 的 manifest（每个 trial 只分配实际出现在其中的 canary；compliance canary 仅在发送了 compliance 轮时计入），只截取本批 Trial ID 的 Relay/Provider 日志行（本批时间窗仅作为无 batch ID 旧结果文件的辅助防护），再运行 `relay7508.scan`；到达 Relay 却未收到注入的 C2 trial 会以 `c2_attack_not_delivered` 警告列出。每个成功 trial 中 `external_attempted=True` 的轮次必须各有一条 Relay 记录，并各有一条 Provider 记录（Relay 记录了转发错误时除外）；关卡拒绝的轮次不应有记录。不一致的 trial 以 `evidence_incomplete` 排除出泄漏率；日志文件缺失或存在不完整 trial 时，Runner 和 `runner.leakscan` 返回非零退出码。输出与结果文件同名的 `.manifest.json`、`.relay.jsonl`、`.provider.jsonl`、`.leak.json` 和 `.leak.csv`；失败 trial 不计入泄漏率，并作为 missing-from-manifest 显示。默认日志为 `logs/relay.jsonl` 与 `reports/provider_ingress.jsonl`，可用 `--log name=path` 修改，`--no-scan` 跳过；也可对已有结果运行 `python -m runner.leakscan reports/runs/<文件>.jsonl`。
- 预注册主矩阵为七个配置（4,200 trials）；`C1-M1_M2` 和 `C2-M1_M2` 仅用于补充组合策略验收，单独报告。
